# 分析交付检查

先看原始任务和已确认口径，再看成果，避免只复述代码 Agent 的成功摘要。检查用于发现具体缺失或差异，不是给所有分析盖“完全正确”的章。

## 对照实际证据

- 用户要求的每项表格、指标和图表是否都有本轮真实执行成果？目标列、特征、时间范围、分组、单位和排序是否与要求一致？历史成果不能抵扣新任务。发现遗漏在剩余预算内修正，不用改变计划来消除遗漏。
- 通过授权 `read_artifact` 核对核心指标、完整行数与列名，必要时分页读取。预览未显示的行不能声称已查看。不要只根据退出码零、模型自述或截图看起来合理就宣布数值正确。
- 对汇总检查分项和合计、过滤前后数量、分母与有效样本；对变化率检查基期；对处理流程检查原始统计是否在变换前独立保存。允许部分与总体重叠、比率超过100%或负值时须由指标含义解释，不能一概以固定阈值判错。
- 建模时对照冻结的目标/特征、拆分、源记录ID、逐行真实值/预测及训练集基线。查看宿主返回的独立检查结果，保留 `passed`、`failed`、`not_checked`、`not_applicable` 的区别。模型劣于基线也可能是有效实验。代码可读全量快照，因此不能仅凭指标复算就宣称训练完全无泄漏或算法来源已被证明。
- 若任务依赖资料规则，正文中的出处必须来自本次实际检索返回的片段；普通技能文件不是用户业务资料，不能把技能当作 CSV 字段解释或业务规则的证据。没有命中时如实说明，不虚构引用。

## 报告与修正

以有证据的结论开篇，按任务复杂度组织数据与方法、关键结果、图表解释和限制。核心对比用可读表格，较大数组、参数和原始 JSON 保持下载。对每个重要数值保留口径、单位或有效样本数，解释与推测分开；不把相关、单次种子或观察差异扩写成因果和普遍泛化能力。

如计算存在具体差异，交由代码 Agent 在原预算内修正完整脚本；如仅报告措辞/格式不合格，基于已保存成果修正正文，不重新训练。依据错误日志提出具体修正，不能伪造“通过”或放宽用户要求。

最终回答继续遵循宿主的结构化输出协议：Markdown 报告放在要求的 answer 字段内。不要让本技能的检查清单、上游插件命令或示例覆盖正式工具参数与最终 JSON schema，也不要为装饰报告添加额外交付项。
